answer: |
  **Q：你这套框架分了这么多层（系统服务 / IPC / 同步异步 / OSAL / 驱动 / 基础设施 / 平台），为什么这么分层？驱动怎么抽象？为什么不直接调 HAL？**

  **A（你怎么答）：**
  **为什么分层**：**解耦 + 可移植 + 可测 + 语义统一**。驱动只依赖 **OSAL** 接口（任务/信号量/互斥锁/队列/事件/定时器/临界区/内存），**看不到具体 RTOS 的 API**，将来换平台/换 RTOS 只改**平台层实现**，业务与驱动不动。

  **驱动怎么抽象（C 里的面向对象）**：不同外设（GPIO/CAN/USART/SPI/I2C）抽象成**统一设备接口**（open/close/read/write/ioctl/控制回调），上层通过**接口指针**调用——**结构体 + 函数指针 = 接口/多态**，这就是「面向接口编程」的落地。具体驱动实现这组函数指针，框架只认接口。

  **对应的设计模式**：
  - **OSAL = 抽象工厂 / 策略**：统一接口，不同 OS 提供不同实现，上层只依赖接口 → **换 OS 不改业务**。
  - **驱动模型 = 接口 + 多态（虚表）**：不同外设实现同一组接口，可替换、可扩展、可测。
  - **workqueue = 生产者-消费者 / 异步**。

  **依赖倒置（SOLID 的 D）**：**上层依赖抽象接口，不依赖具体实现**——这是「可移植、可替换、可测」的根。

## 深读

### 分层的作用
```
业务/驱动 ── #include OSAL ──► platform/osal/xxx.h(纯接口)
                                  │ 默认实现(FreeRTOS版)
                                  ▼
                        freertos/*.c (调用 FreeRTOS API)
```
- **换 OS** 只换 `xxx.c`，业务不动；还能用 **宿主 OSAL mock** 做单元测试（不必真跑 RTOS）。

### C 的接口 = 结构体 + 函数指针
```c
typedef struct {
  int (*open)(void*); int (*read)(void*, char*, int); int (*write)(void*, const char*, int);
} DeviceOps;
```
- 上层 `ops->read(...)` 不认识具体设备 → 多态调用。这就是你驱动模型的底层。

### SOLID 里最常考的 D（依赖倒置）
> 上层依赖抽象，不依赖具体。你驱动依赖 OSAL 而非具体 RTOS，就是依赖倒置的落地。
