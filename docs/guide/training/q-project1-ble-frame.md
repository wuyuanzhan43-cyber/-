answer: |
  **Q：你用 BLE 把数据传上去，怎么处理粘包/拆包？怎么确定一帧完整？**

  **A（你怎么答）：**
  串口/BLE 传上来的是**字节流**，没有帧边界，所以**自己定义协议帧**并**用有限状态机（FSM）逐字节打捞**：

  1. **帧结构**：`帧头 + 长度字段 + 数据 + 帧尾 +（可选 CRC）`。
  2. **多字节帧头**（如 `0xA5 0x5A`）——单字节帧头在数据段出现会**产生假帧头**，双字节把误判率降到 **1/65536**。
  3. **长度合理性检查**：`Length > MAX` 或 `=0` → 丢弃；**超时保护**（某状态停留太久 → 强制回 `STATE_HDR1`）。
  4. **转义/字节填充**：数据段遇到 `0xA5 → 0x7D 0x01`、`0x7D → 0x7D 0x00`，接收反解（SLIP/PPP 做法），**消除帧头歧义**。
  5. **校验**：CRC（比简单校验和强一个数量级），数据错丢弃。

  **关于 BLE 要说清楚（别硬撑）**：JDY-18 是 **BLE 透传模块**，底层 BLE 协议栈由模块封装（GATT 服务/特征值、MTU、连接参数等），我负责**应用层透传 + 组帧 + 断句 + 掉线/粘包处理**。**承认边界 + 说明边界内做了什么**，比吹「我写了 BLE 栈」更稳。

  **2.5s 停顿自动断句**：应用层检测**静默/停顿间隔**切分，配合**掩蔽时间（debounce）** 防止误切。

## 深读

### 一帧完整怎么判（伪代码思路）
```
状态: HDR1 -> HDR2 -> LEN -> PAYLOAD -> CRC -> OK
逐字节:
  匹配 HDR1 -> 进 HDR2
  匹配 HDR2 -> 进 LEN
  读长度 -> 确认 <= MAX -> 进 PAYLOAD
  收 QUANTITY 字节 -> 进 CRC
  CRC 对 -> 一帧完整; 不对 -> 丢弃回 HDR1
  任何一步停留太久(超时) -> 回 HDR1
```

### 为什么多字节帧头 + 转义
- **单字节帧头**（如 0xAA）若在数据段出现 → 误判成帧头。
- **双字节帧头**把误判率降到 1/65536，**转义**则彻底消除「数据里恰好有帧头字节」的歧义。

### 用哪种缓冲装字节流
- **环形缓冲**（固定数组 + 头尾指针），中断里只存字节、主任务解析；**单写单读可无锁**。
- 结合 `ds/q-ring-buffer`、`bs/q-uart-deep`（§十 鲁棒帧解析）一起看。
