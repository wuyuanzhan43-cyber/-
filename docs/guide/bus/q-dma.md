answer: |
  **轮询**：CPU 不断查询设备状态（如寄存器）是否就绪，**简单**，但**占满 CPU**、实时性差，适合短/低频/简单场景。
  **中断**：设备就绪时 CPU 暂停当前工作去处理，**省 CPU**、实时性好；但每次都有**中断开销**（现场保存/恢复、上下文切换），**大量数据仍需 CPU 一趟趟搬**。
  **DMA（直接内存访问）**：让 **DMA 控制器**在内存与外设（或内存↔内存）之间**自动搬运数据**，**CPU 几乎不参与**数据搬运，只需“发起 + 接收完成/错误中断”，实现**极高的吞吐、极低的 CPU 占用**，适合**大块、高速、连续**数据（存储、ADC/缓冲、显示、网络）。
  取舍：**轮询=简单占 CPU；中断=省 CPU 但仍由 CPU 搬；DMA=CPU 基本不搬，吞吐最高但配置复杂、要地址/长度/完成回调、注意缓存一致性与总线占用**。通常组合：DMA + 完成中断。
why: |
  本质是**“谁搬数据、搬多久”**的问题。轮询/中断靠 CPU 字节级搬移，多核时代仍浪费 CPU；DMA 把搬运交给独立硬件引擎，CPU 只做**控制与善后**，是为“大块数据高效传输”而生的。
  嵌入式里大**吞吐**场景（刷新屏、采集大量数据、读写大块存储、拷贝 buffer）几乎必然用 DMA。代价是配置复杂、要处理 DMA 完成/错误中断、缓存一致性（Cache coherency）与地址对齐。

## 深读

### 三种方式对比

| 维度 | 轮询 | 中断 | DMA |
|---|---|---|---|
| CPU 参与度 | 全程占 CPU | 处理+搬运占 CPU | 仅控制(发起/完成) |
| 数据搬运 | CPU | CPU | DMA 控制器 |
| 实时性 | 差 | 好 | 好 |
| 吞吐 | 低 | 中 | 高 |
| 复杂度 | 最低 | 中 | 高 |
| 适用 | 简单/低频 | 中频 | 大块/高速 |

### DMA 完整流程（以“外设→内存”为例）

1. CPU 配置 DMA：源地址、目的地址、长度、方向、完成回调。
2. 启动 DMA，CPU 去干别的。
3. DMA 控制器按配置在**内存与外设**之间搬运（或内存↔内存）。
4. 传输完成触发**完成中断**，CPU 处理善后（如置标志、通知任务）。

### 为什么 DMA 吞吐高、CPU 省

因为**数据不经过 CPU**。中断里 CPU 还是要 `while` 逐字节/逐字搬运；DMA 是独立硬件并行搬运，尤其在高速、大量、连续数据时差异巨大。

### 关键坑（面试常问）

1. **缓存一致性（Cache Coherency）**：DMA 往内存写，CPU 缓存里可能是旧值；要在搬运前 `dma_map_single`/`flush_cache`，搬运后 invalidate。嵌入式里这是最容易出错的地方。
2. **地址/长度对齐**：DMA 常要求地址按某种对齐（如字/总线宽度），长度在某边界。
3. **总线占用**：DMA 占总线带宽，多个 DMA 或与 CPU 争带宽需评估。
4. **完成回调/错误**：用 DMA 完成中断处理状态。
5. **零拷贝/描述符**：Linux 里 `dma_map`、`spi_sync`、`io_uring`、`sendfile` 等本质都大量依赖 DMA/零拷贝换性能。

### 与内核接口

- Linux：`dma_alloc_coherent`、`dma_map_single`、`dma_unmap_*`、`dmaengine`、外设驱动 `dma_request_chan`。
- 裸机/RTOS：配置 DMA 控制器寄存器 + 完成/错误中断 + 地址回填。

### 常见追问

- 为什么 DMA 仍要中断？——DMA 完成需要**通知 CPU 才去做善后**（DMA 本身不跑业务逻辑），所以“DMA 搬运 + 完成中断”是标配。
- 什么时候不该用 DMA？——数据量小、频率低、一次性/低频、或者配置开销远超收益时；小数据用轮询/中断反而划算。
- 轮询比中断好在哪？——无上下文切换开销、无竞态、实时性可控（适合超高频微操作），但占 CPU。

> 📌 一句话记忆：**轮询=简单占CPU，中断=省CPU仍靠CPU搬，DMA=硬件引擎搬运、CPU只善后；大块高速数据首选“DMA+完成中断”。**
