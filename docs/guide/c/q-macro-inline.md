answer: |
  **宏（`#define`）**：**预处理阶段**文本替换，**无类型、无作用域、无返回值语义**，展开可产生副作用（如 `#define SQUARE(x) ((x)*(x))` 若 `x` 有表达式会先算两次）。适合**常量、简单表达式、代码片段**。
  **内联函数（`inline`）**：**编译期**处理，有**类型检查与作用域**，像普通函数但可能被编译器展开（避免调用开销）；**有参数类型、返回值、重载（C++）**，无宏的副作用与括号坑。
  **静态断言（`static_assert`/`_Static_assert`）**：**编译期**断言常量表达式，不满足则**编译失败**；用于检查 `sizeof`、对齐、宏定义、平台假设等编译期约束（强于运行时 `assert`）。
  选型：**常量/无条件复用 → 宏；需要类型安全/复杂逻辑/可调试 → 内联函数（或普通函数）；编译期约束 → 静态断言**。宏是“文本替换”，内联是“函数”，静态断言是“编译期校验”。
why: |
  三者层次不同：宏在**预处理**（无类型、易副作用、难调试），内联在**编译**（类型安全、可展开），静态断言在**编译期检查**（早发现错误）。
  嵌入式里常见宏定义的坑：**展开副作用、括号缺失、运算符优先级、多次求值**；所以更推荐**内联函数 + 类型化常量（`const`/`enum`）+ 静态断言**，只有纯文本替换场合才用宏。面试常考“为什么用 `inline` 替宏”。

## 深读

### 三者对照

| 维度 | 宏 #define | 内联函数 inline | 静态断言 static_assert |
|---|---|---|---|
| 阶段 | 预处理（文本替换） | 编译 | 编译期检查 |
| 类型检查 | 无 | 有 | 编译期常量 |
| 作用域 | 无 | 有 | — |
| 副作用 | 易有（多次求值/括号坑） | 无 | — |
| 是否可调试 | 难 | 可 | 编译错误提示 |
| 典型用途 | 常量/简单表达式/代码片段 | 频繁小函数、类型安全 | sizeof/对齐/平台假设 |

### 宏的经典坑

```c
#define SQUARE(x) x*x
int s = SQUARE(1+2);   // 1+2*1+2 = 5 (而非 9)
// 修正：((x)*(x))，但仍可能多次求值 x
```

- **括号缺失**：要加外括号与每参数括号。
- **多次求值**：`MAX(a++, b)` 中 `a++` 可能被算两次。
- **无类型**：传入不同类型可能出问题。
- **无作用域**：宏名全局可见，易污染。

### 内联函数的优点

```c
static inline int square(int x){ return x*x; }
```

- 有**类型检查**、作用域、返回值，可调试。
- 编译器可展开内联，避免函数调用开销。
- 无宏的副作用/括号/多次求值坑。
- `static inline` 常用于头文件小函数（避免链接冲突）。

### 静态断言（编译期）

```c
_Static_assert(sizeof(int) >= 4, "int must be >= 4 bytes");
_Static_assert(offsetof(struct S, b) == 4, "layout mismatch");
```

- 编译期检查常量条件，不满足直接编译失败，**在构建期就发现**平台/布局假设错误。
- 强于运行时 `assert`（`assert` 只在 debug/运行时检查）。

### 嵌入式实践

- **常量**：用 `#define N 10` 或更好 `const`/`enum`（类型安全）。
- **小函数**：用 `inline`/`static inline`，避免宏。
- **编译期约束**：用 `_Static_assert`（如校验结构体大小、对齐、平台位宽）。
- **纯文本替换/条件编译**（`#ifdef` 等）仍需宏。

### 常见追问

- 为什么用 inline 替宏？——类型安全、无副作用、括弧坑少、可调试；编译器还能展开。
- 宏一定是错的吗？——不是，常量、条件编译、简单替换仍需宏。
- `static inline` 为什么加 static？——避免多个编译单元重复定义符号导致链接冲突（头文件使用）。

> 📌 一句话记忆：**宏=预处理文本替换（无类型、有副作用）；inline=编译期类型安全函数；static_assert=编译期常量校验。优先 inline+const+assert。**
