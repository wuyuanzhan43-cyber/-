answer: |
  `volatile` 告诉编译器：该变量的值可能被本程序控制流之外的方式改变，编译器**不能**把它当作普通变量优化。
  具体表现为：① 不能把它的值缓存到寄存器（每次读取必须真实地访问内存/设备）；② 不能省略对它的读写赋值操作。
  适用于：内存映射 I/O（MMIO）寄存器、由中断或信号处理的共享变量、多线程/多任务共享且没有其它同步机制的标志位、以及常见的嵌入式硬件寄存器访问。
why: |
  编译器为了让程序跑得快，会把变量放到寄存器里缓存，并默认变量只会在代码里被改。一旦外部（硬件、中断、别的线程）悄悄改了它，编译器缓存的旧值就成了**脏数据**。
  加上 `volatile` 就等价于每次都要去「真实源头」取一次，牺牲一点优化，换取数据不出错。
  注意它**不保证原子性、不提供内存屏障**，多线程要配合锁/原子操作；也不能解决指令乱序问题，此时需真正的编译屏障（如 GCC `asm volatile("" ::: "memory")` 或 `__sync_synchronize`）+ 硬件屏障。

## 深读

### 编译器在做什么优化？

对普通变量执行：

```c
int x = 0;
while (x == 0) { /* busy wait */ }
```

编译器可能把 `x` 读进寄存器后就**不再重新读取内存**，于是循环条件永远成立，死循环。这正是嵌入式里常见的坑：`x` 是中断里的标志位，主循环想等它置位，结果编译器“以为”它永不变化。

### 为什么 volatile 是“读内存”的开关

加了 `volatile` 后，每次访问都生成一次真实的 `load/store` 指令，被称作**防止“寄存器缓存”与“删减读写”**（编译器优化细节详见`gcc 优化等级与 volatile`）。但不代表性能一定会崩——对 MMIO 寄存器来说，你本来就要读写真实设备地址，这是必须的。

### 典型场景

| 场景 | 是否用 volatile | 说明 |
|---|---|---|
| 内存映射寄存器（MMIO） | ✅ 必须 | 寄存器值被硬件改变，必须每次真实读写 |
| 中断设置的标志位 | ✅ 建议 | 需要配合适当的内存屏障 / 关闭优化 |
| 多线程共享标志 | ⚠️ 不充分 | 需要原子操作或锁，volatile 不含原子性/内存序 |
| 纯计算局部变量 | ❌ 不必要 | 只会拖慢性能 |

### volatile 的局限性（高频追问）

- **不保证原子性**：`volatile int` 的读改写（如 `++reg`）不是原子的，仍可能被打断。
- **不提供内存屏障**：处理器可能乱序执行，volatile 不能保证顺序，需要 `__sync_synchronize`/`rmb`/`wmb` 或 C11 `atomic`。
- **对 struct 成员无效**：`volatile struct` 只是对每个成员的访问都被视作 volatile，但成员间顺序仍可能被打乱。

### C11 时代的变化

C11 引入了 `_Atomic` 与 `atomic_*`，把「不要优化（volatile）」和「原子性 + 顺序（atomic）」分离得更清楚。新代码优先用标准原子操作，volatile 留给 MMIO/寄存器场景。

> 📌 一句话记忆：volatile = **“别把它当普通变量省着用，去真实源头读”**；但它治不了原子性与乱序。
