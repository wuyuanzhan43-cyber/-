answer: |
  **字符设备（char device）**：以**字节流**访问，无固定块结构，通过 `file_operations` 实现 `open/read/write/ioctl` 等；适合串口、键盘、LED、传感器等**按字节顺序读写**的设备。常由`read/write`直接进设备。
  **块设备（block device）**：以**块（块大小，如 512B/4KB）**为单位访问，有固定大小与寻址，通常有缓存与块 I/O 调度；适合磁盘、SD、eMMC、Flash 等存储介质。访问经 VFS → 块层 → 请求队列 → 驱动。
  区别核心：**访问粒度与抽象**——字符设备面向字节流，块设备面向“可寻址的固定块”；块设备要处理缓存、合并、调度顺序；字符设备相对直接。
  两者都用**设备号（主设备号+副设备号）**标识，通过 `register_chrdev`/`register_blkdev` 注册，由 `mknod` 创建设备节点（或热插拔自动创建）。
why: |
  这是 Linux 设备模型的**两大类抽象**：字符设备提供“像文件一样读字节”的最简单接口，适合控制/流式外设；块设备提供“可随机寻址、性能优化的存储”接口，适合大容量存储。
  理解两者差异，才能选对注册接口与驱动写法，理解为什么存储设备要讲块、要缓存，而控制外设走字节流直通。

## 深读

### 对照表

| 维度 | 字符设备 | 块设备 |
|---|---|---|
| 访问单位 | 字节流 | 块（512B/4KB…） |
| 是否可寻址 | 通常顺序 | 可寻址（block number） |
| 数据通路 | VFS → 驱动 read/write | VFS → 块层 → 请求队列 → 驱动 |
| 缓存/调度 | 简单/无 | 有页缓存 + I/O 调度 |
| 典型设备 | 串口、LED、GPIO、传感器 | SSD/SD/eMMC/磁盘 |
| 操作接口 | `file_operations` | `block_device_operations` + 块请求 |
| 注册 | `register_chrdev` | `register_blkdev` |
| 设备节点 | `/dev/xxx` | `/dev/xxx`（分区） |

### 为什么存储要走“块层”

块设备读写**按块、随机、可能并发**，所以内核在块层做：

- **页缓存**：读命中内存，写先入缓存。
- **I/O 调度/合并**：把相邻块合并、排序，减少设备寻道/提升吞吐。
- **请求队列**：将读写组织成 request，交给驱动的 `request_fn`（或 bio/mq 新架构）。

因此块设备驱动的复杂度主要在“块请求处理 + 缓存/调度语义”，字符设备更直接。

### 嵌入式主流存储

- **NAND/eMMC/SD/SPI-NOR** 通常做成**块设备**（或走 MTD + 块层），需磨损均衡、坏块管理等。
- **SPI Flash** 也可用 MTD/MTD-utils，或封装为块设备提供文件系统。
- 新兴：**ubi/ubifs、ext4、f2fs** 等文件系统的“块”依赖。

### 字符设备 vs “字符型”其实是设备模型之一

注意：Linux 还有**网络设备**（`net_device`，走网卡/socket，不走文件）与**杂项设备**。字符/块/网络是三大类，面试常考字符与块的区别。此外：

- **主设备号**：标识驱动类型；**副设备号**：区分同一驱动下的多个实例/分区。
- 热插拔：通过 `udev`/`mdev` 依据内核信息自动创建设备节点。

### 常见追问

- 为什么块设备要缓存而字符设备不那么需要？——块设备的“随机读改写 + 大块吞吐”很适合缓存合并；字符设备（如串口）是流式、实时，缓存意义小还增延迟。
- 字符设备能做成存储吗？——能（如某些设备做 ioctl/protocol-based 存储），但性能/通用性不如块设备，且文件系统通常需要块接口。
- 一个设备既是字符又是块？——一般选一类；但有的驱动可同时注册。

> 📌 一句话记忆：**字符设备=字节流直通（串口/LED），块设备=可寻址的块+缓存+调度（存储）。**
