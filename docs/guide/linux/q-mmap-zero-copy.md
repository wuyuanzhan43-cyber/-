answer: |
  **mmap**（内存映射）：把文件/设备的一段映射到进程的**虚拟地址空间**，之后进程用普通内存访问（指针/数组）读写文件，**省去 read/write 的拷贝**。背后是内核把**页表**指向对应物理页（与 page cache 共享），从而**用户态与内核态共享同一份内存**，实现**零拷贝/共享内存**。
  典型用途：
  - **文件映射**：`mmap` 直接读文件（`open → mmap → 访问`），减少 `read` 的系统调用与拷贝。
  - **共享内存**：多个进程 `mmap` 同一段（`MAP_SHARED`，匿名或文件），用于**进程间共享**。
  - **零拷贝传输**：`sendfile`/`splice` 在**内核态**直接搬运，不经过用户空间拷贝。
  注意：`mmap` 是**按页映射**，要页面大小对齐；有地址空间消耗、需 `munmap` 解除；写回时机与 `msync` 相关。
why: |
  **减少拷贝 = 减少 CPU 与内存带宽占用，提升吞吐**。传统 `read`+`write` 要在内核↔用户各拷贝一次；`mmap`/`sendfile`/`splice` 通过**页表共享或内核态直搬**，避开不必要的拷贝。
  嵌入式/高性能场景（大文件、视频帧、日志、网络转发）常用 `mmap`（读文件/共享）或 `sendfile`/`splice`（内核态转发）来优化。

## 深读

### 传统 read/write 的拷贝开销

```
磁盘/文件 -> page cache(内核) -> copy_to_user -> 用户缓冲
                                     ↑ 一次拷贝
用户缓冲 -> 内核 -> 设备/网络            ↑ 再一次拷贝
```

### mmap 如何省拷贝

```
磁盘/文件 -> page cache(内核) 
                └─ 把页表指向 page cache 的物理页
用户进程访问(如 buf[i]) -> 直接命中该物理页 (零拷贝/共享)
```

- `mmap` 建立虚拟地址↔物理页映射，用户态访问即读写 page cache，**无需 copy**。
- 多个进程可 `MAP_SHARED` 共享同一映射 → **进程间共享内存**。
- `MAP_PRIVATE` 写时复制（COW），读共享、写复制。

### 零拷贝的系统调用级手段

| 手段 | 说明 |
|---|---|
| `mmap` + `write` | 读映射后写，省一次拷贝 |
| `sendfile(out, in, ...)` | 内核态从文件直接发送，不经过用户空间 |
| `splice` | 内核态在两个 fd 间搬运 |
| `vmsplice` | 用户缓冲区映射进管道，避免拷贝 |
| `copy_file_range` | 内核态拷贝文件 |

### 关键注意点

- **按页映射**：`mmap` 长度要**页大小（4KB）对齐**，偏移也需页对齐；最后一次映射大小应取整到页。
- **地址空间消耗**：映射占用虚拟地址空间，多/大映射需留意；用完 `munmap`。
- **写回/一致性**：`MAP_SHARED` 写回文件，可用 `msync` 强制；要考虑与 DMA/缓存一致性。
- **与缓存一致性**：映射后读写的可见性，信号 `/` 进程间共享要配合原子/同步。

### 典型应用

- **读取大文件/数据库/配置文件**：`mmap` 随机读比 `read` 高效。
- **共享内存 IPC**：`shm_open` + `mmap`，多进程共享大块。
- **视频/图像帧缓冲**、**网络转发**（`sendfile`）。

### 常见追问

- `mmap` 为什么能零拷贝？——把页表指向内核 cache 的物理页，用户态直接命中，避免 copy_to_user。
- `mmap` 一定更快吗？——小文件/高频随机小读可能不如 read；大块/随机访问/共享更合适。
- 为什么映射要页对齐？——MMU 以页为单位建页表，长度/偏移要对齐到页边界。
- 不 `munmap` 会怎样？——地址空间被占、映射未释放，可导致“映射泄漏”。

> 📌 一句话记忆：**mmap=把文件/共享内存映射进虚拟地址空间，页表共享/零拷贝；sendfile/splice=内核态直搬；用于大文件、共享IPC、帧缓冲、网络转发。**
