answer: |
  **系统调用**是内核提供的接口（`read/write/open/close/fork` 等），通过陷入（`svc`/`syscall`）从用户态进入内核态，**必须在后端有内核实现**，开销较大。
  **库函数**（`printf`、`fread`、`fwrite`、`malloc`、`strlen`）由**C 标准库/封装层**提供，可能是一层封装：**底层往往还是调用系统调用**（如 `fread` 内部用 `read`，`fwrite` 用 `write`），也可能是纯用户态实现（如 `strlen`、`memcpy`，不进内核）。
  区别核心：**抽象层次与是否陷入内核**——库函数是用户态的封装/工具，系统调用才是内核的入口。库函数常加**缓冲**（如 `stdio` 有用户态缓冲）来减少系统调用次数，提升性能。
why: |
  **库函数更上层、更便捷**（带缓冲、错误处理、跨平台）；**系统调用更底层、更直接**（真正访问内核/硬件）。二者**不是对立**：库函数经常封装系统调用，但**不是所有库函数都走到内核**。
  理解这层区别：`printf` 会走系统调用（写设备/文件），而 `strlen/memcpy` 纯用户态不进内核；`fwrite` 有缓冲，`write` 直接系统调用。嵌入式里要**减少系统调用次数**（用缓冲/大块读写）就理解了为什么 `fread` 比多次 `read` 高效。

## 深读

### 关系图

```
用户程序
  └─ 库函数 printf / fread / malloc ...
      ├─ 有的纯用户态: strlen, memcpy, 部分数学运算
      └─ 有的封装系统调用: fread→read, fwrite→write, malloc→brk/mmap
           └─ 系统调用: read/write/open/fork... (陷入内核)
```

### 对照表

| 维度 | 系统调用 | 库函数 |
|---|---|---|
| 提供者 | 内核 | C 标准库/封装层 |
| 层次 | 内核接口（最底层） | 用户态封装/工具 |
| 是否陷入内核 | 是（进入内核态，开销大） | 有的是，有的不是 |
| 缓冲 | 无（直接） | 常带用户态缓冲（stdio） |
| 跨平台 | 依赖 OS | 标准库相对可移植 |
| 出错处理 | 返回负值/errno | 包装后错误处理更友好 |

### 为什么 printf 比 write 慢/快

- `write` 每次**陷入内核**，直接写。
- `printf` 走 `stdio`，**有用户态缓冲**，攒够一批再 `write`，从而**减少系统调用次数**。
- 所以**批量+缓冲**能提升性能：多次小 `write` 不如一次大 `write`/`fwrite`，也解释了为什么嵌入式日志常开环形缓冲或整段输出。

### 嵌入式里的实践

- **减少系统调用**：一次读大块（`read`/`fread` 大缓冲），而非多次小读。
- **选择合适接口**：需要直接、可重定向下，用系统调用；需要缓冲或格式化，用库函数。
- **底层设备/驱动**：直接走系统调用（`open/read/write/ioctl`），`stdio` 只是可选封装。

### 常见追问

- 所有库函数都会系统调用吗？——不是，`strlen/memcpy/strcmp` 等纯内存/字符串操作不会陷入内核。
- `printf` 一定会进内核吗？——`printf` 格式化后在用户态，写时经 `write`/缓冲进入内核；若写入的是内存映射/文件描述符也类似。
- 为什么要缓冲？——减少系统调用（陷入开销很大），提升吞吐。

> 📌 一句话记忆：**系统调用=内核入口（陷入、开销大）；库函数=用户态封装（有的内部调系统调用、有的纯用户态），常带缓冲减系统调用次数。**
