answer: |
  CPU 通过**特权级别**区分用户态与内核态（如 ARM 的 User/System 与 SVC、x86 的 Ring3/Ring0）。用户态权限受限，不能直接访问硬件、I/O、内核内存；内核态拥有最高权限，可执行特权指令、访问全部内存与设备。
  从用户态进入内核态的**唯一正规途径是“陷入”**：系统调用（swi/ecall/syscall）、异常、中断。它们触发特权级切换，把控制权交给内核，由内核代表程序访问敏感资源。
  进入内核态的代价：要保存用户现场、切换栈、切换特权级，较慢，因此要**减少系统调用次数、批量操作**（如 read/write 大缓冲、mmap、io_uring/netlink）。
why: |
  这是现代 OS 的**保护与隔离基石**。用户程序不可信，必须被限制在隔离的用户空间运行，不能随便读写内核/外设，否则一个 bug 就会让整机崩溃或被攻击。
  系统调用是“受控的通行证”：程序提出请求，内核在特权级下核验并代做，从而实现安全性、稳定性与可移植性。

## 深读

### 场景：一段“很慢”的代码

> 用户：我用 `write(fd, buf, 1)` 一字节一字节写给串口/文件，数据量大时很慢。为什么？怎么改？

**这不是“算法慢”，是“系统调用次数多”。** 下面带你把它定位清楚。

### 一、排查链条（现象 → 定位 → 原因 → 改法）

1. **先量化**：用 `strace` 看系统调用**次数与耗时**、`ltrace` 看库调用、`perf` 看热路径。发现 `write` 被调了几万次 → 怀疑**陷入开销**。
2. **判断**：`write()` 每次都是一次**系统调用**（触发陷入）。一字节一写 = **每字节陷入一次**，开销巨大。
3. **定位根因**：陷入的固定开销 = **保存现场 + 切用户栈→内核栈 + 特权级切换 + 返回**。这不随数据量增长，**次数**才是主因。
4. **改法**：**缓冲/批量**——攒一批再写（`fwrite` 自带用户态缓冲，或自己攒 buffer），一次 `write` 大块；或 `mmap` 零拷贝、`io_uring` 批量异步、`sendfile`/`splice` 内核直转。

> 关键结论：**“一次调用处理更多数据”比“多次调用处理同一批数据”快得多。**

### 二、体系推导 / 记忆链（把相关点串成一条线）

```
你的应用 write()
  → libc(fwrite/stdio) 封装（带缓冲）
  → 把 fd/缓冲/长度 放到寄存器（ARM64 用 x0-x2、系统调用号在 x8；ARM32 用 r0-r2、系统调用号在 r7）
  → 执行 syscall / svc 指令（触发陷入）
  → CPU 切到内核栈、切特权级（用户态→内核态）
  → 内核按系统调用号查 sys_call_table → sys_write → ksys_write
  → VFS：file->f_op->write（函数指针，多态）→ 具体驱动
  → copy_from_user 拷入内核缓冲 → 驱动写设备
  → 返回：恢复现场、切回用户态
```

一条链把 **特权级 + 陷入 + 调用约定(寄存器) + 系统调用表 + VFS/驱动 + copy_user** 全串起来。

### 三、时序 / 状态机（一次陷入的“状态迁移”）

```
用户态(写) --[syscall/svc]--> CPU: 保存现场 + 切内核栈 + 特权级提升
   --> 内核态(处理) --> 恢复现场 + 特权级降级 + 切回用户栈
   --> 用户态(返回，得到结果)
```

- **两次特权级切换 + 一次栈切换 + 一次现场保存/恢复** = 陷入的固定开销。
- 这解释了“系统调用比函数调用贵很多”。

### 四、参数 / 公式（开销在哪、怎么量化）

- 单次陷入开销 ≈ **保存/恢复现场 + 换栈 + 特权级切换 + 内核查表 + 可能 TLB/cache 变化**。
- **总开销 ≈ 系统调用次数 × 单次陷入开销** → 所以**减少次数**是主线。
- 对比：一次普通函数调用 ≈ 压栈 + 跳转，**没有特权级切换**。
- 优化公式化：`少调用(批量) + 少拷贝(mmap/零拷贝) + 异步批量(io_uring)`。

### 五、数据结构 / 布局（背后涉及的“东西”）

- **用户态 / 内核态地址空间隔离**：用户进程只映射自己的页面；内核有独立地址空间（这就是用户态拿不到内核内存的原因）。
- **内核栈 + 用户栈**：陷入后切到**内核栈**（每进程/线程一个），返回用回**用户栈**；两者分离避免用户态碰内核栈。
- **系统调用表 `sys_call_table`**：一个“**系统调用号 → 函数**”的数组，内核按号分发。
- **`struct file` / `file_operations`**：VFS 层数据结构，`f_op->write` 是**函数指针**（让内核用统一接口调不同驱动）。

### 六、工程踩坑与改法

- **坑**：高频小读小写（每字节一次系统调用）→ 慢、浪费 CPU → **缓冲/批量**。
- **坑**：用户态直接访问内核/设备地址 → 越界/崩溃 → 用 `copy_to_user/from_user` 或驱动接口。
- **坑**：以为 `write` / `read` 很快 → 实际每次都是陷入 → 少调用。
- **坑**：忘关/误用文件描述符，`strace` 可看出多余系统调用 → 关闭未用 fd。
- **坑**：中断里做**会陷入**的事（如系统调用/阻塞）→ 中断上下文不能阻塞 → 只做短、原子操作。

### 七、常见追问与满分回答

**Q：为什么系统调用比函数调用慢？**
A：函数调用只有压栈+跳转；系统调用要**特权级切换 + 保存/恢复现场 + 切换内核栈 + 内核查表 + 可能的 TLB/cache 变化**，所以贵一个数量级。因此要**少调用、批量**。

**Q：怎么让它快？**
A：① 一次读/写大块（减少陷入次数）；② `mmap` 零拷贝（减少内核↔用户拷贝）；③ `io_uring` 批量异步提交；④ `sendfile/splice` 内核直转。核心都是**少陷入、少拷贝、批量**。

**Q：用户态能直接操作硬件吗？**
A：主流 OS 下不能，必须经系统调用/驱动（内核态代办）；裸机没有这一层保护，可直接。（加分：MCU 用 MPU 做折中分区保护。）

**Q：系统调用和中断都进内核，区别？**
A：发起方不同——系统调用是**用户主动**、同步、有语义，发生在用户上下文、可调度；中断是**硬件异步**打断，时机不定、可能发生在任意上下文、不能阻塞。所以中断处理要短、可重入。

> 📌 一句话记忆：**系统调用=用户态(受限)→陷入→内核态(代办)→返回；陷入贵在“特权级切换+换栈+保存现场”，所以少调用、批量、mmap/io_uring；用户态拿不到内核内存（地址空间隔离）。**
