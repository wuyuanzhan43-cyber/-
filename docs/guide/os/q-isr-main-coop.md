answer: |
  **中断与主循环/任务协作**：中断（ISR）做**快速、必须**的事情（如置标志位、读寄存器、发通知），把**较重的处理交给主循环/任务**。
  常用协作模式：
  - **标志位（flag）**：ISR 置位一个 `volatile` 标志，主循环/任务**轮询**该标志并处理，处理后清标志。
  - **队列/信号量**：ISR 里 `FromISR` 发队列/信号量，主任务阻塞等待并处理（更“事件驱动”）。
  - **回调/钩子**：ISR 调用注册的回调（需保证回调短、可重入、不阻塞）。
  **线程安全要点**：
  - 共享标志用 `volatile`（防编译器缓存），但**不保证原子**；简单置位/清零通常够，复杂的用原子/关中断。
  - ISR 与主循环若访问同一数据结构，需**关中断**或用**单写单读环形缓冲**（无锁）。
  - ISR 里**不能阻塞**（睡眠锁/队列阻塞 take），只能 give/发。
why: |
  **中断必须短**（拉长会丢中断/破坏实时性），而真正的业务处理往往较长或需要上下文 → 所以**“中断置标志/发事件，主循环/任务处理”**是标准分工。
  关键是把“**快速、原子、可重入**”留在 ISR，把“**可阻塞、较长**”丢给任务/主循环，并用**线程安全**的机制（flag/队列/环形缓冲+关中断）同步，避免数据竞争与丢事件。

## 深读

### 常见协作模式

| 模式 | ISR 做什么 | 主循环/任务做什么 | 同步 |
|---|---|---|---|
| 标志位 | 置 `volatile` flag | 轮询 flag、处理、清 flag | flag（简单） |
| 队列 | `xQueueSendFromISR` | `xQueueReceive` 阻塞处理 | 队列（事件驱动） |
| 信号量 | `give` | `take` 等待 | 信号量 |
| 环形缓冲 | 写缓冲/更新索引 | 读缓冲 | 无锁(单写单读)/关中断 |

### 经典的“中断置标志”模式

```c
volatile int flag = 0;
void uart_isr(void){
  // 快速：置标志
  flag = 1;
}
void main_loop(void){
  while(1){
    if(flag){
      flag = 0;     // 清标志
      process_data();
    }
  }
}
```

- `flag` 要 **`volatile`**，否则编译器可能缓存、主循环看不到变化。
- **丢事件隐患**：若 ISR 连续发生两次而主循环只处理一次，可能漏掉（可用计数/队列改为“每事件一次”）。

### 为什么 ISR 不能阻塞

- ISR 运行在**别人的上下文**，且非任务，不能调度/睡眠。
- 阻塞的锁/队列 `take` 会让系统“卡在中断里”，永不恢复。
- 所以 ISR 只用**非阻塞**版本（`FromISR`、置 flag、`give`）。

### 线程安全要点

- **共享 flag/数据**：用 `volatile` + 简单原子（或关中断/关抢占）保护。
- **复杂结构**（环形缓冲、链表）：**单写单读**可无锁（配合内存屏障）；否则用**关中断/自旋锁（禁抢占）**，但要短。
- **ISR 与任务/主循环访问同一数据**须同步，否则数据竞争。

### 常见追问

- 为什么 ISR 只置 flag 而把重活丢主循环？——缩短中断时间、避免丢中断/实时性下降；重活需要上下文与可阻塞性。
- 丢事件怎么避免？——用**计数**或**队列**（每个事件一个消息），而非单布尔标志。
- flag 为什么用 volatile？——防编译器缓存，主循环每次读真实值；但 volatile 不保证原子，复杂场景要原子/关中断。

> 📌 一句话记忆：**ISR 只做“置标志/发事件/读寄存器”（快、原子、不阻塞），重活丢主循环/任务；共享数据用 volatile+关中断/无锁环形缓冲。**
