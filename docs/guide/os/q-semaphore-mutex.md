company: [华为, 中兴]
keywords: 信号量 互斥锁 计数信号量 二进制信号量 所有权 优先级继承
answer: |
  **互斥锁（Mutex）**：用于**互斥**，同一时刻只有一个任务能持有；强调**所有权**（只有持有者能解锁），通常带**优先级继承**，适合保护共享资源的临界区。
  **信号量（Semaphore）**：用于**同步/计数**，本质是一个计数器（二进制信号量=0/1，计数信号量=N）；不关心“谁持有”，主要用来“发信号”（如任务等待事件），也用于资源池计数（如固定数量的缓冲）。
  **核心区别**：
  - 用途：Mutex=互斥（只允许进入）；Semaphore=同步/计数（标记事件/资源数量）。
  - 所有权：Mutex 有 owner，必须由 owner 释放；Semaphore 无 owner，任何任务都可释放（V）。
  - 优先级：Mutex 可做优先级继承，Semaphore 通常没有。
  - 递归性：Mutex 有的支持递归；Semaphore 无“递归”概念。
why: |
  两者**都能阻塞**，但语义不同：Mutex 是“门只有一个能进”，Semaphore 是“这里有一个/多个车牌”。
  弄混会导致两个经典 bug：① 用信号量护临界区 → 可能被别的任务意外“释放”导致互斥失效、或遭遇优先级反转；② 用互斥锁做同步/发事件 → 没有“稍等一会”或“计数多次”的能力，且 owner 语义不符。

## 深读

> 📖 【临界区 / 上下文切换】
> - **临界区**：访问共享资源、必须互斥的代码段；同一时刻只允许一个任务进入。
> - **上下文切换**：保存当前任务的寄存器/PC/SP、恢复另一个任务的；进程级还要切换页表/TLB（成本更高）。

### 语义对照

| 维度 | 互斥锁 Mutex | 信号量 Semaphore |
|---|---|---|
| 本质 | 互斥：同一时刻一人占用 | 计数器：同步/资源计数 |
| 取值 | 无锁/有锁 | 二进制(0/1) 或 计数(N) |
| 所有权 | 有 owner，必须 owner 释放 | 无 owner，可被任意任务释放 |
| 用途 | 保护临界区/共享资源 | 任务同步、发事件、资源池 |
| 优先级继承 | 通常支持 | 通常不支持 |
| 典型场景 | 保护共享变量/外设 | 生产者-消费者、等事件、信号 |
| 类比 | 只准一人进的厕所门 | 一个可计数的通行牌 |

### 什么时候用哪个

- **保护共享资源**（变量、队列、外设）→ 用 **Mutex**。
- **通知“某事发生了”**（事件/标志）→ 用 **二进制信号量**。
- **管理一批相同资源**（N 个缓冲槽）→ 用 **计数信号量**。
- **生产者-消费者** → 信号量控制“空/满”，配合消息队列。

### 典型“误用”与后果

1. **用信号量护临界区**：某个任务在错误时机多 `release()` 一次，导致“门多开了一扇”，两个任务同时进入临界区 → 数据竞争。
2. **用互斥锁做跨任务“唤醒等待”**：owner 语义要求“谁锁谁开”，若用别的任务去开，语义混乱。
3. **在中断里用会阻塞的信号量/锁**：中断上下文不能阻塞 → 崩溃或死锁；正确做法是中断里“发信号”（如队列/信号量 give），任务里再处理。

### RTOS 常见 API 对应（FreeRTOS 为例）

- 二进制信号量：`xSemaphoreCreateBinary` + `give/take`。
- 互斥锁：`xSemaphoreCreateMutex`（带优先级继承）/ `xSemaphoreCreateRecursiveMutex`（递归）。
- 计数信号量：`xSemaphoreCreateCounting`（资源池）。

### 常见追问

- 信号量能互斥吗？——能，二进制信号量可当互斥用，但**没有所有权与优先级继承**，不如 Mutex 语义清晰、安全。
- 互斥锁能当信号量吗？——不理想，因为它强调 owner 且不便于“计数多次事件”。
- 中断里能用信号量吗？——只能“give”（发，且用中断安全版本 `FromISR`），不能“take 阻塞”。

### ★ 参考题解精华

> 摘自 FreeRTOS 内核面试题集（V11.1.0 源码），补充「互斥锁底层复用 + 优先级继承/反转的源码细节」。（反转的场景化推演见「RTOS 优先级反转 q-priority-inversion」。）

**① 底层：互斥锁、信号量、队列共用一套 `Queue_t`**

| 字段 | 数据队列 | 信号量 | 互斥锁 |
|---|---|---|---|
| `uxItemSize` | >0 | 0 | 0 |
| `pcHead` | 真实缓冲 | 指向自身 | `NULL`（类型标记） |
| `uxMessagesWaiting` | item 数 | 资源计数 | 1=开锁 0=上锁 |

- `uxItemSize==0` → `prvCopyDataToQueue/FromQueue` 不做 `memcpy`，只动计数器。互斥锁额外用 `pcHead==NULL` + union 里的 `xMutexHolder`（持有者）、`uxRecursiveCallCount`（递归深度）实现“所有权 + 优先级继承”。
- 这也解释了“为什么信号量没所有权 / 互斥锁有主人”：信号量只操作一个计数器（任何任务都能 give/take），互斥锁则记录持有者与继承状态。

**② 优先级反转怎么发生 + 继承怎么治（源码细节）**

- 经典场景 H/M/L：L 持锁 → H 抢入申请锁被阻塞 → M（与锁无关）就绪**抢占 L** → L 得不到 CPU → **H 被无名地拖进无限期等待**。
- **无继承**：能反转；**有继承**：H 申请锁时，内核检测到 H 优先级高于持有者 L，**临时把 L 提升到 H 的级别**，M 抢不动 L → L 尽快释放 → H 恢复后 L 级回退。
- 源码：Take 成功后 `pxQueue->u.xSemaphore.xMutexHolder = xTaskIncrementMutexHeldCount()`；阻塞前 `xTaskPriorityInherit(xMutexHolder)` 提级；Give 时 `xTaskPriorityDisinherit()` **降回“等待者中的最高优先级”或基础优先级**（继承是临时、传递的）。
> 💡 一句话：**反转=高优被“持锁的低优 + 插队的中优”拖住；互斥锁=真带继承（记录 xMutexHolder + 临时提级/归还），裸信号量只计数、不救。**

> ⚠️ 别把“互斥锁很完美”当唯一结论：**继承只是压缩等待，仍可能有死锁/并发下降**——见「RTOS 优先级反转（q-priority-inversion）」的继承 vs 天花板对比，以及「死锁四条件（q-deadlock）」。选型与误用见本卡「什么时候用哪个」。

> 📌 一句话记忆：**Mutex = “只准一人进的门”（有主、带继承）；Semaphore = “计数/发信号的牌”（无主、可计数）。**
