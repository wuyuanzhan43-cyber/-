answer: |
  在互斥锁/信号量之上，更细的同步原语：
  - **条件变量（condition variable）**：与互斥锁配合，线程**等待某条件满足**再继续（`wait` 释放锁并睡眠，`signal/broadcast` 唤醒）。解决“**等条件而非忙等**”，适合**生产者-消费者/任务就绪等待**。
  - **读写锁（rwlock）**：**读共享、写独占**，读多写少时提升并发；读不互斥、写需独占（可读者优先/写者优先）。
  - **原子操作（atomic）**：单条指令完成读-改-写（`atomic_*`/`__atomic_*`/内建），**无锁**实现计数/标志位（无锁），避免加锁开销，但需内存序。
  外加**自旋锁**（忙等，短）与**互斥锁**（睡眠，长）。C11/C++ 提供 `atomic`/`mutex`/`condvar`。
why: |
  复杂场景需要**不同粒度的同步**：
  - **条件变量**让线程**等待而**不忙等（比轮询高效），与锁配合实现“**等到某条件**”。
  - **读写锁**在**读多写少**时提高并发（读共享）。
  - **原子操作**做**无锁计数/标志**，低开销。
  理解每种原语的**适用与粒度**（忙等/睡眠/原子/读共享/写独占），才能写出**正确高效**的并发代码，避免忙等浪费、锁竞争、死锁。

## 深读

### 条件变量（与互斥锁配合）

```c
pthread_mutex_lock(&m);
while (!condition) pthread_cond_wait(&cond, &m);  // 释放锁+等待；唤醒后重新拿锁
pthread_mutex_unlock(&m);
```

- `wait` 释放锁并睡，被 `signal`/`broadcast` 唤醒后**重新拿锁**继续。
- 用 `while` 而非 `if` 防**虚假唤醒（spurious wakeup）**。
- 解决“等条件”而不空转。

### 读写锁

- **读共享**：多个读者可同时持有；**写独占**：写者需要独占。
- 适合**读多写少**（配置文件、缓存）。
- 注意**读者优先可能饿死写者**，写者优先则读者稍等。

### 原子操作（无锁）

```c
atomic_int count = 0;
atomic_fetch_add(&count, 1);   // 原子自增
if (atomic_load(&count) == N) { ... }
```

- 单条原子指令完成读-改-写，无锁、低开销。
- 需注意**内存序**（acquire/release）保证可见性与顺序。

### 常见追问

- 条件变量为什么要配互斥锁？——需要锁来保护“判断条件”的临界区，避免竞态。
- 为什么用 `while` 而非 `if`？——防**虚假唤醒**。
- 读写锁什么时候用？——读多写少（读者并发，写者独占）。
- 原子操作比锁好在哪？——无锁、无阻塞、低开销；但需内存序、只适合简单读改写。

> 📌 一句话记忆：**条件变量=等条件(配锁,不忙等)；读写锁=读共享写独占(读多写少)；原子=无锁读改写(计数/标志)；按场景选粒度。**
