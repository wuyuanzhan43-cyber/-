answer: |
  **自旋锁（spinlock）**：**忙等待**——拿不到锁就一直**空转（spin）**占用 CPU，不退出临界尝试；代价是**占 CPU 但不会阻塞/调度**，适合**临界区极短**（几行）、且**禁止睡眠**的上下文（**中断上下文/原子上下文/关抢占**）。持有自旋锁时会**禁抢占**（甚至关中断），因此临界区必须非常短，否则死锁/长时占 CPU。
  **睡眠锁（如 mutex/信号量/读写锁的睡眠版）**：拿不到锁就让出 CPU**睡**去，不空转；适合临界区较长、**允许睡眠**的**进程上下文**（可以 `schedule`）。阻塞式，等待时不占 CPU。
  选择依据：**临界区是否可能很长/是否在原子上下文**。原子上下文只能用自旋锁；进程上下文且临界区长 → 用睡眠锁。**自旋锁不可在睡眠上下文长时间持有，睡眠锁不可在原子上下文使用**。
why: |
  核心是“**能不能让步**”：自旋锁不让步（空转），是为了**原子上下文**能用（那里不能调度/睡眠）；睡眠锁让步（睡），优化 CPU 让渡，但必须有**可调度的上下文**。
  错用很危险：在中断/原子上下文用睡眠锁 → 阻塞导致系统卡死；在进程上下文长持自旋锁 → 白占 CPU、可能死锁（preempt 被关）。所以“**临界区极短用自旋锁，长/可睡眠用睡眠锁**”，且严格区分上下文。

## 深读

### 对比

| 维度 | 自旋锁 spinlock | 睡眠锁 mutex/信号量 |
|---|---|---|
| 拿不到锁 | 忙等（空转占 CPU） | 让出 CPU 睡眠 |
| 是否可睡眠/调度 | 不能 | 可以 |
| 适用上下文 | 原子/中断/关抢占 | 进程上下文 |
| 临界区长度 | 极短 | 可较长 |
| 持锁时能否 schedule | 不能 | 可以 |
| 风险 | 空转占CPU、死锁(关抢占)、中断延迟 | 被调度延迟、优先级反转（需继承） |
| 典型 | 保护短临界区、中断与任务共享数据 | 保护需要长时间操作/可睡眠的共享资源 |

### 自旋锁为什么“禁抢占/关中断”

- 自旋锁内含“关抢占”，避免另一任务抢走 CPU 后也来争同一把锁 → 造成**持锁者被抢占而死锁**。
- 若在**中断里用自旋锁**，中断优先级高于任务，可能“中断要锁但任务持锁被中断打断” → 需配合关中断或专门版本。
- 因此自旋锁必须**短**：持锁期间不能调用可能睡眠的函数、不能做耗时操作。

### 睡眠锁为什么不能在原子上下文用

中断/原子上下文**不能调度**，调用会阻塞的取锁（如 `mutex_lock`）会“等一个永远不会来的调度” → 死锁/崩溃。所以原子上下文只能用**不会睡眠**的自旋锁等。

### 实战选型

- 保护**几行赋值/位操作、共享临时** → 自旋锁。
- 保护**较长的数据处理、对外设读写、可睡眠的资源** → 睡眠锁（mutex）。
- **读写锁**：读多写少用 rwlock（读共享、写独占）。
- **顺序锁（seqlock）**：写少读多、写者更新快时用。

### 常见追问

- 为什么自旋锁空转浪费 CPU 还要用它？——原子上下文不能调度，只能忙等；且临界区短，空转时间可忽略。
- 自旋锁会死锁吗？——会：持锁者被更高优先级抢占且去争同一把锁（关抢占可避免）；或在中断里再取同一把非中断安全锁。
- 怎么写才安全？——临界区极短、不调用可睡眠函数、注意中断与上下文、必要时用关中断+自旋。

> 📌 一句话记忆：**自旋锁=忙等占CPU、禁睡眠，适合原子/中断上下文与极短临界区；睡眠锁=让出CPU、可调度，适合进程上下文与较长临界区。**
