answer: |
  死锁是多个线程/进程互相等待对方所占资源、导致谁都推进不下去的状态。产生死锁需要同时满足**四个必要条件**：
  ① **互斥**：资源一次只能被一个线程占用；
  ② **持有并等待（请求保持）**：已持有一个资源，又去申请别的资源且不放；
  ③ **不可剥夺**：资源在未用完前不能被别人强行夺走；
  ④ **循环等待**：存在一个线程-资源的循环等待链（A 等 B、B 等 A）。
  只要破坏其中**任意一个**条件即可避免死锁。常用手段：按序（固定顺序）申请资源、一次全部申请（破坏持有并等待）、超时/回退、破坏循环等待、用**资源分配图**检测。
  经典算法：**银行家算法**（安全序列判据）、**资源分配图 + 环路检测**、**时间戳排序**（破坏循环等待）。
why: |
  死锁的本质是“**资源争夺 + 相互等待**”。四条件是死锁的**必要条件**（必须同时成立才会死锁），因此是判断/预防的抓手：不必四者全都有才叫互斥，而是“必须四者同时成立才会死锁”，所以破坏任一条件就能破除。
  嵌入式里常因**任务与中断、锁的顺序不一致**而引发死锁，典型如“多任务共享多把锁时按不同顺序加锁”导致循环等待。

## 深读

### 经典产生场景

```c
// thread A            // thread B
lock(&m1);             lock(&m2);
lock(&m2);             lock(&m1);   // 互相等待对方
```

A 持 m1 等 m2，B 持 m2 等 m1 → 循环等待 → 死锁。

### 四个必要条件详解

| 条件 | 含义 | 破解思路 |
|---|---|---|
| 互斥 | 资源一次只被一人用 | 尽量少用互斥资源；用可重入/可复制资源 |
| 持有并等待 | 拿着一个还去要另一个 | 一次性申请全部所需资源 |
| 不可剥夺 | 用不完不能被抢 | 允许超时/抢占/回退 |
| 循环等待 | 存在环形等待链 | 规定**全局一致加锁顺序** |

### 常见的预防手段

1. **全局加锁顺序**：所有代码都按同一顺序（如 m1 永远先于 m2）申请锁——最简单有效，直接消除循环等待。
2. **一次性申请所有资源**：破坏“持有并等待”，但可能降低并发度、造成资源浪费。
3. **超时 + 回退**：申请不到就放弃已持有的，破坏“不可剥夺”。
4. **资源分配图 + 环路检测**：检测到环就采取动作（如回退一个）。
5. **银行家算法**：分配前判断是否处于“安全状态”，进行预防性分配——开销大，工程中少用。

### 死锁 vs 活锁 vs 饥饿

- **死锁**：互相等待，谁都不动。
- **活锁**：都在动但反复让路，仍无法前进。
- **饥饿**：某线程长期拿不到资源（如优先级反转），但系统仍在推进。

### 嵌入式中的死锁高发点

- **任务与中断共享资源**：中断里加锁（可能关中断/用自旋锁），顺序不当。
- **多任务持有多个锁**：加锁顺序不一致。
- **互斥锁与信号量混用**：在中断上下文用了不可用的同步原语。
- **回调/嵌套**：持锁时调用会再次加锁的函数。

### 常见追问

- “互斥”是必要条件，但那它不是所有资源都互斥啊？——对，所以打破互斥并不总是可行（有些资源天生互斥），通常更实际的是**统一加锁顺序**。
- 四条件缺一还会死锁吗？——不会，四个必须**同时**成立才死锁，这也是预防的切入点。
- 怎么检测已经发生的死锁？——资源分配图找环，或设超时/看门狗观察是否卡死。

> 📌 一句话记忆：**“互持不可循”（互斥/持有并等待/不可剥夺/循环等待），破坏任意一个就能防死锁；最实用的是统一加锁顺序。**
