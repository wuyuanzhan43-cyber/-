answer: |
  中断上下文**不能**直接做的事主要是：① **阻塞/睡眠/调度**（不能用会阻塞的锁、`sleep`、`alloc` 且在需要时可失败；中断里不能用信号量 `take` 阻塞、不能 `kfree` 靠睡眠的分配、不能调用会调度/睡眠的函数）；② **长时间占用 CPU**（会造成其它中断丢失、实时性破坏）；③ **执行高危、宕机级操作**（如重入、死锁、空指针等直接崩系统）。
  原因：中断上下文**不是任何任务**，它打断的是某个正在运行的上下文，且**不能切换到别的上下文**。如果阻塞，系统就等于“卡死在中断里”，所有调度停止。
  正确做法：**中断里只做最小、最快的动作**，把耗时/可阻塞的工作用**底半部（底半部/工作队列/tasklet/软中断）或队列、信号量通知任务**去完成；中断里可用**短临界区（关中断/自旋锁，禁抢占）**，但绝不能用会睡眠的互斥锁。
why: |
  中断是**异步、高优先级、不可预测**的。它一旦进入，就在“别人的上下文”里运行；若在此阻塞或调度，就会破坏调度器的前提，导致系统卡死或丢失事件。所以中断处理要**极短、原子、不阻塞、可重入**，把重活放到可调度的上下文。

## 深读

### 中断上下文的特殊之处

- **没有“当前任务”**：中断打断了某个任意上下文，本身并非一个可被调度的任务。
- **抢占被禁用 / 不参与普通调度**：大部分 RTOS/内核里，中断期间不允许切换任务。
- **不能阻塞**：阻塞意味着“等待某条件”，但没有任何上下文能替它等待 → 系统挂死。
- **要极短**：中断耗时越长，其它中断/实时任务被拖得越久，导致丢中断或超时。

### “不能做”清单（嵌入式面试常背）

| 动作 | 是否允许 | 说明 |
|---|---|---|
| `xSemaphoreTake`（阻塞） | ❌ 不能 | 中断里不可阻塞；只能用 `give` 的 `FromISR` 版 |
| 睡眠/延时（sleep/msleep） | ❌ 不能 | 会调度/阻塞 |
| 可能睡眠的内核分配（malloc 需睡眠时） | ⚠️ 谨慎 | 用中断安全/原子版本 |
| 长时间循环/Hook | ⚠️ 避免 | 别霸占 CPU |
| 关中断的**长**临界区 | ⚠️ 谨慎 | 会加剧中断延迟 |
| 重入自身 | ⚠️ 注意 | 要可重入，避免自我打断死锁 |
| 非原子地操作共享变量 | ❌ 不能 | 要用原子/关中断/自旋锁保护 |

### 正确姿势：底半部 / 让任务接管重活

中断处理分**上半部**（快、原子）与**底半部**（慢、可调度）：

- **Linux 内核**：快路径在中断处理（top half），慢路径交给 **软中断/tasklet/workqueue**（bottom half）。
- **RTOS**：中断里只做“标志置位 + 发队列/信号量（FromISR）”，真正的处理在**任务/线程**里做。

**最小化中断时间**是关键：中断里只做“把数据存起来/发个通知/置标志”，其余交给任务。

### 中断 vs 轮询 vs DMA（附带高频延伸）

| 方式 | 优点 | 缺点 |
|---|---|---|
| 轮询 | 简单、可控 | 占 CPU、实时性差 |
| 中断 | 省 CPU、实时性好 | 有中断延迟、需可重入 |
| DMA | CPU 几乎不干预大量数据 | 需内存/外设配置、边界处理 |

### 常见追问

- 为什么中断里能用“信号量 give”而不能“take”？——`give` 只是置计数/唤醒等待者，不阻塞、不调度、短；`take` 可能导致阻塞等待 → 不可。
- 中断里非要访问共享资源怎么办？——用**关中断**或**自旋锁（禁抢占）**，但必须短。
- 中断能被高优先级中断打断吗？——可嵌套（取决于是否开了中断优先级/嵌套），需保证可重入、保护共享数据。

> 📌 一句话记忆：**中断里“极短、不阻塞、可重入、不能调度”；重活丢到底半部/任务/队列去做。**
