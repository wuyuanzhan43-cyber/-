answer: |
  **任务栈**是每个任务私有的、**向低地址增长**、大小由 `xTaskCreate` 的 `usStackDepth` 决定。**栈溢出**＝任务栈写过了边界。

  **FreeRTOS 的检测机制**（配置 `configCHECK_FOR_STACK_OVERFLOW`）：
  1. **方法一（=1，水印/哨兵法）**：任务**创建时把整个栈区域填充已知值（`0xa5`）**；**任务切换时**检查栈尾部若干字节是否仍为 `0xa5`——变了说明被溢出覆盖。
  2. **方法二（=2，栈指针越界法）**：任务切换时检查当前 `pxTopOfStack` 是否**超出栈基址 `pxStack`**（向下越出边界），越线即溢出；更可靠（能抓"刚好回位"的情形），开销略大。
  - 检测到溢出时调用 **`vApplicationStackOverflowHook()`**，开发者可在其中**记录/复位/保存现场**；FreeRTOS（方法 2）会把该任务从就绪链移除，避免继续破坏。

  **会导致什么问题**：
  1. **覆盖相邻内存**——别的任务栈、堆、全局变量 → **数据损坏、随机诡异行为**。
  2. **写坏栈帧/返回地址** → 返回时 PC 错乱 → **HardFault** 或跑飞。
  3. **写坏其它任务现场** → 上下文/调度错乱。
  4. 典型症状：**系统偶尔崩、HardFault、跑飞、任务间数据互洗**，且**难以稳定复现**。
why: |
  栈是任务私有的，**越界会破坏"栈下/栈上"的相邻内存**——在 RTOS 里很可能正好是**另一个任务的栈、堆管理器、或全局数据**。于是出现"**偶尔崩、难复现、改一点就好了**"的非确定性 bug，这是嵌入式最棘手的一类。
  所以：
  - **为什么填充 `0xa5` 再做切换核对水印**：只靠"我能看到栈被写"不够；填哨兵值，一旦正常代码没写到的尾端变了，就知道越界了。**剩多少 `0xa5` = 还剩多少栈**。
  - **为什么要 `vApplicationStackOverflowHook`**：栈溢出发生时就该**记录现场、复位或安全停机**，而不是让它继续破坏下去。
  - **诱因**：**深度递归、超大局部数组、底层库（printf/浮点）栈消耗、任务栈配太小**——定位思路见 Q21/Q22。

## 深读

### 两种检测对比

| 方法 | `configCHECK_FOR_STACK_OVERFLOW` | 原理 | 特点 |
|---|---|---|---|
| 水印/哨兵 | 1 | 创建时填 `0xa5`，切换时核对栈尾是否保持 | 省，但"刚好回位"可能漏检 |
| 栈越界 | 2 | 切换时看 `pxTopOfStack` 是否超出 `pxStack` | 更可靠，较费 |

- 推荐 `=2`（越界检查），并在溢出触发**钩子**里记录现场、复位或安全折返。
- **初始化填充**：启动时用 `memset(pxStack, 0xa5, size)`，崩溃时**检查水位线**可知最大用了多少栈。

### 寄存器/源码级：判断"往哪边溢"

- Cortex-M 栈**向低地址增长**，任务栈顶 `pxTopOfStack` 从栈高地址往下走。
- **向下溢出**：`pxTopOfStack < pxStack`（越过栈基址），往往写到**相邻的其它任务栈/堆**。
- 源码检查点：方法 2 在 `vTaskSwitchContext`/`xPortPendSVHandler` 附近判断 `uxTopOfStack` 与 `pxStack` 关系；方法 1 核对 `pxStack` 附近是否还是 `0xa5`。
- 部分配置用 **`pxEndOfStack`**（栈增长向上时用栈尾），FreeRTOS 两种增长方向都用 `pxStack`/`pxEndOfStack` 组合判断。

### 溢出破坏什么（内存布局）

```
任务A栈(向低地址增长)
 ┌──────────────┐  <─ pxTopOfStack(当前栈顶)
 │ 正常局部变量  │
 │ [返回地址栈帧]│  ← 溢出写坏 → PC 错乱 → HardFault/跑飞
 ├──────────────┤  <─ pxStack(栈基址)
 │  下一段内存   │  ← 很可能是别的任务栈/堆/全局 → 被污染
 └──────────────┘
```

### 常见诱因与排查

| 诱因 | 说明 |
|---|---|
| **深度递归/深调用** | 每层函数都占栈帧，递归深度大易超 |
| **超大局部数组** | 如 `char buf[4096]` 直接放栈上，远超配额 |
| **库函数消耗** | `printf`/`snprintf`/浮点/`malloc` 可能吃很多栈 |
| **任务栈配太小** | `usStackDepth` 太小，或低估了最坏调用深度 |

- 常见追问的排查法见 `q-stack-overflow-debug`（Q22）：用**栈水位/填充 0xa5 + 看 pxStack 剩余量**、**栈溢出钩子**、**IDE 的 Stack Usage 报告**。

### 工程场景

- **症状**：任务偶尔崩；崩溃点 PC/数据地址在"另一个任务"的栈区间。
- **根因/排查**：确认是**哪个任务**溢出（钩子/`pcTaskName`/`pxStack` 归属）；看**栈水位**（`uxTaskGetStackHighWaterMark` 近 0）；找**吃栈的调用**（深递归/大数组/printf）。
- **对策**：给该任务**增大 `usStackDepth`** 并**实测水位留余量**；把大数组移堆/静态区、用轻量 printf、限制递归；开启检测 + 钩子提前拦截。

### 进阶追问链

1. **Q：为什么用 `0xa5` 填充（常见 0xaa/0x55）？** → `0xa5` 非零、有规律，正常代码不会恰好连续写；切换时尾端丢了 `0xa5` 即被写到。其它值也行，关键是**配合水位估计**。
2. **Q：检测到溢出后 FreeRTOS 会怎样？** → 调 `vApplicationStackOverflowHook()`；若实现里没处理（默认空/打印），FreeRTOS（方法 2）会把任务**从就绪链移除并标记**，避免继续破坏，但不保证系统不崩——钩子里要处理。
3. **Q：栈溢出能百分百抓到吗？** → 不能。水印法在"刚好回位"可能漏检；越界法也有窗口。所以**栈配额留足余量**，以**最坏调用深度实测**为准。
4. **Q：为什么往低地址溢？** → Cortex-M 栈向下增长；栈顶指针减小。溢出常发生在"调用越来越深/局部变量越来越大"时把 `pxTopOfStack` 压过 `pxStack`（栈基址）。

> 📌 一句话记忆：**任务栈向低地址增长、大小靠 usStackDepth；FreeRTOS 用填充0xa5水印(方法1)或pxTopOfStack越界pxStack(方法2)检测，并触发vApplicationStackOverflowHook；溢出会破坏相邻内存→数据损坏、PC错乱HardFault；诱因是深递归/大局部数组/库栈消耗/栈配太小。**
