answer: |
  **保存内容**：任务上下文切换保存的是"**让该任务未来能在任意时刻精确恢复**"的完整 CPU 现场，组织成一个**上下文帧（context frame）**放在任务栈上：
  1. **硬件压的异常帧**：`R0–R3/R12/LR/PC/xPSR`（进入 PendSV 时硬件自动压栈）。
  2. **手动保存的寄存器**：`R4–R11`（被调用者保存寄存器，FreeRTOS 移植层汇编手动压入）。
  3. **可选浮点扩展帧**：使能 FPU 且使用浮点时的 `S0–S15/FPSCR`。
  4. **任务栈顶本身**：切换后 SP 指向栈顶，栈顶就是"当前上下文帧"的起始。

  **保存在哪里**：保存在**该任务自己的私有栈（PSP 指向的任务栈）**，**并非整体拷贝**——而是"**借一次 PendSV 异常进出 + 手动压/弹 R4–R11**"把现场组织在栈上。**栈顶位置记录在 TCB 的 `pxTopOfStack` 字段**（它必须是 TCB 第一个成员，因为移植汇编直接按首地址读它）。

  **切换**：选到新任务后，从新任务 TCB 读 `pxTopOfStack` → `PSP = pxTopOfStack` → 恢复栈上寄存器（弹 R4–R11、硬件弹 8 字）→ `BX LR` 用 `EXC_RETURN` 选出正确栈与模式 → 从新任务被切出的位置继续。**不拷贝任务栈，只换指针 + 压/弹寄存器**。
why: |
  最容易问懵的是"任务上下文到底存哪儿"。答案不是"存到一个全局数组"，而是"**存在每个任务自己的栈上，TCB 用 pxTopOfStack 记住栈顶**"。这样：
  - **恢复是按指针完成的**：切到哪个任务，就把 `PSP` 设成哪个任务 TCB 的 `pxTopOfStack`，再弹栈。
  - **每个任务的现场独立可达**：各任务栈互不干扰，调度器只需维护"当前是哪个任务"（`pxCurrentTCB`）。
  - **为何 R4–R11 必须手动存**：它们是 callee-saved，编译器函数级保护不足以覆盖多级嵌套调用；只有 RTOS 在切换时把它们压到栈上，任务才能完整复原。
  这解释了 FreeRTOS「**两阶段切换**」：内核层记账（把任务挪到目标链）+ 移植层汇编（压/弹寄存器、换指针）。

## 深读

### 任务栈上的上下文帧（示意）

```
任务栈(PSP 指向) ── 向低地址增长
┌──────────────────────────────┐
│ ... 任务运行中的局部变量/调用栈 │
├──────────────────────────────┤
│ R4..R11     ← FreeRTOS 手动压 │ ← 上下文帧起点
│ S0..S15/FPSCR（可选浮点）     │
├──────────────────────────────┤
│ R0                          │ ← 硬件压的异常帧(进入 PendSV 时)
│ R1                          │
│ R2                          │
│ R3                          │
│ R12                         │
│ LR(EXC_RETURN)              │
│ PC(被切出的下一条)          │
│ xPSR                        │
└──────────────────────────────┘
         ▲ pxTopOfStack 指向这里（TCB 第一个成员）
```

### 上下文帧 vs TCB（"要恢复的寄存器"与"调度元数据"分开）

| 类别 | 内容 | 存在哪 |
|---|---|---|
| **上下文帧（要恢复）** | 8 字异常帧 + R4–R11 + 可选 FPU | **任务自己的栈上** |
| **栈顶锚点** | `pxTopOfStack` | TCB（必须是第一个成员） |
| **调度元数据** | 优先级、状态节点 `xStateListItem`/`xEventListItem`、任务名、栈基址/大小、入口 | TCB |

### 源码级：为什么 `pxTopOfStack` 必须是 TCB 第一个成员

移植层上下文切换汇编（`vPortPendSVHandler`）直接：
```asm
; 保存当前任务现场
mrs  r0, psp           ; 当前任务栈顶
stmdb r0!, {r4-r11}    ; 压 R4-R11
; 把新栈顶写回当前任务 TCB 首字段(偏移0)
LDR  r1, =pxCurrentTCB
LDR  r1, [r1]          ; r1 = pxCurrentTCB(当前任务 TCB 地址)
STR  r0, [r1]          ; TCB[0] = 新栈顶  ← 依赖"pxTopOfStack 是第0成员"
; 选下一个任务
ldr  r0, =pxCurrentTCB ; 再取下次要赋值的 TCB 地址(下个任务)
... vTaskSwitchContext()
; 恢复新任务
ldr  r0, [pxCurrentTCB]; 新任务 TCB
ldr  r0, [r0]          ; 新任务 pxTopOfStack
msr  psp, r0           ; PSP = 新任务栈顶
ldmia r0!, {r4-r11}    ; 弹 R4-R11
bx   lr                ; EXC_RETURN: 硬件弹 8 字, 回新任务被切出点
```
它**不按字段名、不偏移**，直接假设 `TCB 首地址` 就是 `pxTopOfStack`。所以 **pxTopOfStack 必须放第一位**——这是移植层汇编的硬约定。

### EXC_RETURN 在"切回新任务"里的作用

- 恢复现场后 `bx lr`，硬件按 `EXC_RETURN`（存于弹出的 LR）弹回 8 字，并**选回正确栈与模式**：
  - bit2 选 **MSP/PSP**（这里应回 PSP，即"刚切换的任务栈"）；
  - bit4 决定**是否含 FPU 帧**。
- 若 EXC_RETURN 设错（如回到 MSP），切回的任务用错栈 → 跑飞/HardFault。

### 工程场景

- **症状**：任务 A 切到任务 B 后，B 的局部变量变成了别的任务的垃圾数据。
- **根因**：上下文帧没在一个任务的栈上正确组装（如 `R4–R11` 没随切换保存，或 `pxTopOfStack` 写错位置）。
- **排查**：断点在切换处看**任务栈内容**（是否含 8 字 + R4–R11）、看 `pxTopOfStack` 是否指向正确栈顶、看 `EXC_RETURN` 是否回 PSP。
- **对策**：确认移植层"保存顺序/弹栈顺序"与"TCB 首字段"一致；不要改动 `pxTopOfStack` 前的任何字段。

### 进阶追问链

1. **Q：任务切换会不会拷贝整个栈？** → 不会。只把当前任务现场压到**它自己栈**、把新任务栈顶从它 TCB 读出设为 PSP，然后弹栈恢复。是"换指针 + 压/弹寄存器"。
2. **Q：两个任务上下文帧会不会互相覆盖？** → 不会。每个任务用自己栈（PSP 各自独立），上下文帧在各自栈顶；`pxCurrentTCB` 维护"当前是谁"，`pxTopOfStack` 记各栈顶。
3. **Q：`pxTopOfStack` 指向的是栈顶还是帧底？** → 指向**上下文帧的起始（栈顶）**；恢复时从它开始弹（先 R4–R11，再硬件 8 字）。
4. **Q：如果用 `vTaskDelete(self)`，这个上下文怎么办？** → 任务自己被删除，其栈与 TCB 由 Idle 任务回收；上下文帧不再恢复（任务已终止）。

> 📌 一句话记忆：**任务上下文保存＝硬件 8 字 + R4–R11(+可选浮点)组成上下文帧，放在该任务自己的栈上，栈顶由 TCB 首成员 pxTopOfStack 记住；切换＝换指针(PSP=新任务pxTopOfStack)+压/弹寄存器，不拷贝栈；EXC_RETURN 决定回哪个栈/模式。**
