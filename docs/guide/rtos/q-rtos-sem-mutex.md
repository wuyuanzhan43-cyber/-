answer: |
  二者都是 RTOS 的**同步原语**，但**语义不同**：

  ### 信号量（Semaphore）
  （二值/计数）用于**同步、事件、计数**。**没有"所有权"**：任何任务/中断都可以 `xSemaphoreGive`/`xSemaphoreTake`，不绑定持有者。适合"**发生了某件事**""**资源池还剩多少个**"这类语义。

  ### 互斥锁（Mutex）
  用于**互斥、资源独占**。**有"所有权"**：只能由**持有它的那个任务**来解锁（take 后必须由同一任务 give）。**自带优先级继承**，能避免优先级反转。

  ### 关键区别
  | 维度 | 信号量 | 互斥锁 |
  |---|---|---|
  | 用途 | 同步/事件/计数 | 互斥/资源独占 |
  | 所有权 | 无持有者 | 有持有者（须同任务解锁） |
  | 优先级继承 | 无 | 有（避免反转） |
  | 中断里 give/take | give 可用 FromISR | ❌ 不能（牵扯所有权/阻塞） |
  | 计数可累加 | 可（计数信号量） | 不可以（普通互斥锁重入会死锁） |

  ### 怎么选
  - **同步/通知/计数**（"某事发生了"/"资源几个"）→ **信号量**。
  - **保护共享资源/临界区/独占外设**（"一次只能一个人用/改"）→ **互斥锁**（带优先级继承）。
  - 一句话：**"发生了"用信号量，"归我独占"用互斥锁。**
why: |
  面试常背"信号量管同步、互斥锁管互斥"，但更本质的是**所有权与继承**：
  - **信号量无所有权**：谁都能 give，所以表达"**事件/计数**"，give/take 是"发通知/取资源"；也因此**不能保证是同一个锁持有者**来释放。
  - **互斥锁有所有权 + 优先级继承**：只有持有者能 unlock，且持有时低优先级任务被临时提级，**避免高优先级任务等一个"被中优先级插队"的低任务**（优先级反转）。
  - 这两个差别直接决定**能不能把信号量当互斥锁用**——不行：裸信号量做资源保护会**无保护、无继承**，优先级反转就来了。
  - **互斥锁不能进中断**：牵扯所有权 + take 可阻塞，违反"中断里不可阻塞"。

## 深读

### 对比表

| 维度 | 信号量 | 互斥锁 |
|---|---|---|
| 语义 | 同步 / 事件 / 计数 | 互斥 / 资源独占 |
| 所有权 | 无（任意任务/中断可 give） | 有（仅持有者可 unlock） |
| 优先级继承 | ❌ 无 | ✅ 有 |
| 中断里用 | ✅ `xSemaphoreGiveFromISR` | ❌ 不可 |
| 计数 | 二值(0/1) 或 计数(N) | 单 token（二值语义） |
| 递归 | 计数可累加 | 普通互斥锁**重入会死锁**；`RecursiveMutex` 可递归 |
| 典型用途 | 任务唤醒、事件标志、资源池计数 | 保护共享数据、外设、临界区 |

### 源码级：所有权与继承的实现差异

- **互斥锁**在 task 结构里通过 `uxBasePriority`/`uxMutexesHeld` 实现**继承**：
  - `xSemaphoreTake(mutex)` → 若所有权归别人，**阻塞并等待**；拿到锁后记录持有者。
  - `xTaskPriorityInherit()`：当高优先级任务等这把锁时，把**持锁低优先级任务**临时提到高优先级任务级。
  - `xSemaphoreGive(mutex)` → `xTaskPriorityDisinherit()`：**恢复 `uxBasePriority`**。
- **信号量**：只是 `xQueueGenericSend`/`xQueueSemaphoreTake` 的计数增减，**无"持有者"概念**，所以**不自动继承**。

### 典型场景

- **信号量**：
  - **二值信号量**做"任务同步"：ISR `xSemaphoreGiveFromISR` 唤醒一个任务，任务 `xSemaphoreTake` 等待事件。
  - **计数信号量**做"资源池"：N 个同类资源，`take` 取一个、`give` 还一个。
- **互斥锁**：
  - 保护**共享变量/外设/FIFO**：任务 A 加锁、读写、解锁；任务 B 想进则等。
  - 需要**优先级继承**、避免反转的**资源独占**场景。

### 为什么"信号量不能当互斥锁"用

- 信号量**无所有权**：A 拿走的信号量，B 也能 `give` 回来 → `take`/`give` 配对被打断，保护不成立。
- 信号量**无继承**：低优先级持"信号量"时不提级，高优先级等它 → **优先级反转**。
- 所以"保护资源"要用**互斥锁**，而不是"把信号量初值设 1"。

### 工程场景

- **症状**：用"初值为 1 的信号量"保护共享资源后，高优先级任务响应变慢/反转。
- **根因**：信号量无所有权、无继承，把"互斥"当"计数同步"用。
- **对策**：改用**互斥锁**（带继承）；或缩短临界区；能关中断的极短临界区用 `taskENTER_CRITICAL`。

### 进阶追问链

1. **Q：为什么互斥锁自带优先级继承，信号量没有？** → 互斥锁语义是"资源独占、有持有者"，系统知道"哪个任务持锁"，能在高优先级任务等待时把持锁者临时提级；信号量语义是"事件/计数"，无持有者概念，无法做继承。
2. **Q：互斥锁能不能在中断里用？** → 不能。互斥锁 take 可能阻塞（违反中断不可阻塞），且牵扯"所有权由持有任务解锁"，中断不是任务、无法满足所有权。中断里只能用 `FromISR` 版信号量/队列/任务通知。
3. **Q：能用互斥锁做"任务同步"（信号量语义）吗？** → 语义不符。同步是"谁都能触发、谁都能等待"的事件；互斥锁要求"同任务解锁"，做纯同步会很别扭甚至犯错。用信号量/事件组/任务通知更合适。
4. **Q：递归互斥锁（RecursiveMutex）和普通互斥锁？** → 递归互斥允许**同一任务重复 take**（计数式），用于"同一任务内多层调用都持同一锁"；普通互斥锁**同一任务重入会死锁**。

> 📌 一句话记忆：**信号量＝同步/事件/计数，无所有权，中断可用FromISR give；互斥锁＝资源独占，有所有权(同任务解锁)+优先级继承(xTaskPriorityInherit/Disinherit)，不能进中断。"发生了"用信号量，"归我独占"用互斥锁。**
