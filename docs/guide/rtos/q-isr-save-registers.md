answer: |
  Cortex-M 进异常时，**硬件（NVIC/内核）自动压栈**保存一组"**异常进入栈帧（exception frame）**"到**当前栈**：

  - **基础帧（8 个字 / 32 字节）**：`R0`、`R1`、`R2`、`R3`、`R12`、`LR(R14)`、`PC(R15)`、`xPSR`。
  - **启用 FPU 且使用浮点时**：额外压入**扩展帧**——`S0–S15`、`FPSCR`、一个保留字（是否压入由 **lazy stacking** 和 `EXC_RETURN` 决定，只有被用到的浮点寄存器才会真正入栈）。

  **由谁负责**：
  1. **硬件自动压栈**：这 8 个字（及扩展帧）是内核在响应异常时**自动**压到当前 SP 上的，不需要写代码。所压到的栈取决于当前用什么指针——**未处于异常处理时（thread mode）**压到 `PSP`；**裸机/异常态**压到 `MSP`。
  2. **软件只补"被调用者保存寄存器"**：`R4–R11` 是 callee-saved，被中断打断的代码可能当前正用着它们。这些**通常在任务上下文切换时**由 FreeRTOS 手动保存；而在**单纯的中断里**，编译器会在进入 ISR 的 prologue 里按需保存（ISR 本身是普通 C 函数，遵守 AAPCS）。
  3. **返回由硬件恢复**：异常返回用 **`EXC_RETURN`**（LR 中的特殊值）决定**从哪个栈弹栈、是否含浮点帧、回到哪种模式**，`BX LR` 弹出异常帧、恢复被打断的现场。
why: |
  被问"中断保存哪些寄存器"时，最容易答错成"所有寄存器都保存"。Cortex-M 的**硬件自动压栈**只保存**能让代码继续跑的最小集**（R0–R3/R12/LR/PC/xPSR），因为：
  - **调用者保存寄存器（caller-saved）**：`R0–R3/R12`，函数调用方自己负责保护，中断打断了，先手也被"调用者"保护。
  - **控制流寄存器**：`LR`、`PC`、`xPSR`，必须保存才能**回到被打断处**并恢复状态位。
  - **被调用者保存寄存器（`R4–R11`）** 则由**编译器/RTOS**负责——这才是"任务切换要手动补 R4–R11"的原因。
  分清「**硬件自动压 8 字 / 编译器与 RTOS 补 R4–R11 / EXC_RETURN 决定返回**」三段，就能回答"由谁保存、存到哪、返回怎么恢复"。

## 深读

### 异常进入栈帧（exception frame）结构

Cortex-M 进异常时自动压到栈上的内容（**最高地址是先进栈的**，即 R0 在栈顶之上、xPSR 更深）：

```
地址低 ────────────────────── 地址高
┌───────────────────────────────┐
│ S0..S15（仅 FPU 使用且未 lazy）│ ← 扩展帧（可选）
│ FPSCR + 保留字                │
├───────────────────────────────┤
│ R0                            │ ← 基础帧（8 字，必压）
│ R1                            │
│ R2                            │
│ R3                            │
│ R12                           │
│ LR (EXC_RETURN)               │
│ PC(被打断处下一条)            │
│ xPSR                          │
└───────────────────────────────┘
```

- **LR 里不是普通返回地址，而是 `EXC_RETURN`**（如 `0xFFFFFFF9` 等），低 4 位编码：
  - bit2 → 用 **MSP 还是 PSP** 返回；
  - bit4 → 是否恢复 **FPU 扩展帧**；
  - bit3 → 返回 **handler mode 还是 thread mode**。
- 异常返回 `BX LR` 时，硬件根据 `EXC_RETURN` **弹栈恢复**。

### 谁保存什么（分三层）

| 层 | 谁负责 | 保存什么 | 备注 |
|---|---|---|---|
| 硬件自动 | NVIC/内核 | R0–R3、R12、LR、PC、xPSR（+可选 FPU 扩展帧） | 进异常时自动压到当前 SP，返回时自动弹 |
| 编译器 | C 工具链（AAPCS） | 被调用者保存寄存器 R4–R11、可能被改的寄存器 | 在函数 prologue 里按需保存（ISR 是普通 C 函数） |
| RTOS 移植层 | FreeRTOS 汇编 | R4–R11 + 可选 FPU 状态 + 任务的 PC/LR 等 | 只在**任务切换**时保存到任务私有栈，而非普通中断 |

### 常见追问

- **Q：为什么中断里不用手动保存 R4–R11？**
  A：普通 ISR 是 C 函数，编译器在 entry 处按 AAPCS 保存它会用到的 callee-saved 寄存器，返回时恢复，所以**纯中断**不需要 RTOS 插手。R4–R11 需要 RTOS 手动保存，是针对**任务切换**——因为切出去的任务未来要"原样恢复"，编译器函数级保护不够（可能跨多个函数嵌套调用）。

- **Q：为什么硬件只压 8 个字就够？**
  A：这 8 字（R0–R3/R12/LR/PC/xPSR）足够让 ISR 结束后**精确回到被打断处并恢复状态**。caller-saved（R0–R3/R12）由调用方保护，callee-saved（R4–R11）由编译器/RTOS 保护，分工清晰，硬件只需保"控制流 + 参数寄存器"。

- **Q：浮点寄存器什么时候会压栈？**
  A：启用 FPU 且异常发生时使用浮点（或 lazy stacking 被关闭）才会压 `S0–S15/FPSCR` 扩展帧。**lazy stacking** 默认只在真的用到浮点时现场压栈，减少无浮点中断的开销。是否恢复由 `EXC_RETURN` 的 bit4 决定。

> 📌 一句话记忆：**Cortex-M 硬件进异常自动压 8 字＝R0–R3/R12/LR/PC/xPSR（+可选 FPU 扩展帧）到当前栈；callee-saved R4–R11 由编译器/RTOS 补；返回用 EXC_RETURN 弹栈恢复。**
