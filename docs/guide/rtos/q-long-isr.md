answer: |
  ISR 过长会**成串地破坏系统**，最直接的是三层：
  1. **丢中断/丢数据**：ISR 占着 CPU 不放，排在后面的同/低优先级中断**延迟响应**；若外设**FIFO 溢出**（UART/SPI/ADC），数据直接丢失。
  2. **破坏实时性**：高优先级任务被长时间拖延，**最坏情况响应时间（WCET）失控**，达不到实时指标，抖动变大。
  3. **tick 与调度错乱**：若 SysTick 也被推迟，**系统时钟（tick）不准**，导致延时、超时、时间片全部偏离，任务调度错乱。

  进一步还会：
  - **低优先级任务饿死**：长 ISR 大幅抬高 CPU 占用率，甚至 100% 霸占，低优先级任务长时间得不到运行。
  - **嵌套+栈溢出**：嵌套中断里每个 ISR 占用栈（MSP），深层嵌套叠加长 ISR 可能**栈溢出**。
  - **看门狗误动作**：若喂狗依赖任务，长 ISR 卡住喂狗任务会导致**误复位**。

  结论：**ISR 必须短而原子**——只做"读外设寄存器、清标志、`FromISR` 进队列/置标志/唤醒任务"，重活丢给**任务、底半部或 DMA**。
why: |
  中断是**异步、高优先级、不可预测**的"借道"执行：它一旦进入就占用 CPU，且**不能调度、不能阻塞**。因此它耗时越长，**其它中断和实时任务等待越久**。
  实时系统的核心不是"峰值跑得多快"，而是"**最坏情况响应时间可控**"；长 ISR 直接摧毁这个指标——一个 100ms 的 ISR，就等于让整个系统每 100ms 才有一次反应机会。所以所有嵌入式规范都强调"**ISR 短**"，把它当作实时性的保命线。

## 深读

### 长 ISR 的连锁后果（从近到远）

```
长 ISR 占用 CPU
 ├─ 同/低优先级中断延迟 → 外设 FIFO 溢出 → 丢数据/丢事件
 ├─ 高优先级任务被拖 → 实时响应失控(WCET 超标) → 抖动
 ├─ SysTick 推迟 → tick 不准 → 延时/超时/时间片全错 → 调度错乱
 ├─ CPU 占用率飙升 → 低优先级任务饿死
 └─ 嵌套深 + 栈占用 → MSP 栈溢出 → HardFault
```

### ISR 该做什么 / 不该做什么

| 该在 ISR 做（短、原子） | 不该在 ISR 做（重活） |
|---|---|
| 读外设寄存器 / 清中断标志 | 复杂运算、解析、字符串处理 |
| `xQueueSendFromISR` / `xSemaphoreGiveFromISR` | `vTaskDelay` 等阻塞 API |
| `xTaskNotifyFromISR` 唤任务 | 长循环 / 打印 / 耗时的 malloc |
| 置一个"事件标志" | 可能调用调度器的重入逻辑 |

### 典型场景：收一帧大数据

- ❌ 在 UART ISR 里逐字节解析、组帧、查表、上报——ISR 会很长。
- ✅ ISR 里只把**字节放进环形缓冲/队列（`FromISR`）**,任务里再做组帧、解析、上报；或用 **DMA** 把数据挪进内存，中断只通知"传输完成"。

### 常见追问

- **Q：为什么丢中断而不是"排队"？**
  A：中断是**事件**，不是"任务"。若某中断正在处理，同/更低优先级中断被**挂起**；如果它被屏蔽/超时或外设 FIFO 已满，**事件就丢了**（没有"缓存"机制兜底），只有 `FromISR` 唤醒的任务能等。

- **Q：ISR 太长会栈溢出吗？**
  A：可能。中断用 **MSP**；**嵌套中断**会为每次嵌套**压栈异常帧**。若 ISR 还调用深函数、有大量局部变量，叠加嵌套深度，会把 MSP 用光 → **栈溢出 → HardFault**。

- **Q：到底多长算"太长"？**
  A：原则是**越短越好**，以"不丢其它中断、不破坏最坏响应"为准，典型在**几十微秒~一两百微秒内**完成"存数据/置标志"，重活全丢任务。具体上限由项目最坏情况响应指标决定。

> 📌 一句话记忆：**ISR 过长 → 丢中断/丢数据、实时性崩溃(WCET失控)、tick不准调度错乱、低优先级饿死、嵌套栈溢出、喂狗卡住误复位；所以 ISR 只做"读+清标志+FromISR通知"，重活丢任务/DMA/底半部。**
